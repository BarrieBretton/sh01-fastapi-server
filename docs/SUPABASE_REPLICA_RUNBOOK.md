# SH01 database standby and coordinated switches

This implementation supports a **planned, one-way** database switch while the current database is reachable. It does not claim lossless promotion after the current database has already disappeared. The active Render pair is quiesced, a committed marker is observed on the standby, and only then is the subscriber made writable. A failed switch after that point leaves both public routers in maintenance for operator recovery. No automatic reverse replication is created.

## Operator preparation (one time)

1. Back up both projects and identify which project currently receives n8n writes. Record its slot (`supabase-a` or `supabase-b`), the serving Render pair, and the one live B2 bucket (`b2-a`). Keep the standby project **empty**; the setup script refuses an existing public table or extension. A populated second project requires a separately reviewed migration, never overwrite it.
2. Set `SUPABASE_A_HOST`, `_PORT=5432`, `_USER`, `_DB`, `_PASSWORD` and equivalent `SUPABASE_B_*` variables on **both controllers**. These are direct database credentials, not a Supabase dashboard access token. Provide PostgreSQL client tools `psql` and `pg_dump`. Make the publisher reachable from the subscribing database. Check logical replication privileges and the `wal_level=logical` setting in both project dashboards. Supabase connection routing, privileges, and IPv4/IPv6 availability must be checked against your two projects.
3. Run `python scripts/setup_postgres_subscription.py --source supabase-a --destination supabase-b` from a host that can reach both databases. Inspect the report, backups and database ownership. With an empty destination and an approved maintenance window, rerun with `--apply`. The script creates one `public` marker table, a publication of current `public` tables, and a subscription. A failed partial setup stops for manual inspection; do not repeat `--apply` blindly. `pg_dump` clones schema only; initial rows are copied by the subscription.
4. Monitor `GET /infra/postgres/replica-status?source=supabase-a&destination=supabase-b` with the SH01 control credential. Confirm `ready: true` after initial copy. Keep schema and publication synchronized whenever n8n is upgraded or tables are added; logical replication does not copy DDL or sequence positions. Test an n8n read on a *nonserving* staging copy, and verify the `N8N_ENCRYPTION_KEY` is identical on both Render pairs. Do not point a live standby n8n process at the subscriber.
5. Deploy `cloudflare/control-plane-worker.js` on the **infra-control** Worker with the existing `MEDIA_QUEUE_DB` D1 binding and a new `CONTROL_PLANE_API_KEY` secret equal to the controllers' control-plane API key. Apply `cloudflare/infra_coordination.sql` to that D1 database. Insert its single `global` row with the **observed, current** active Render, Postgres and B2 slots using the commented SQL seed template; do not seed from stale env defaults. Verify `GET /internal/infra-coordination/status` using the `X-API-KEY` header.
6. Set `CONTROL_PLANE_BASE_URL=https://infra-control.vivojaymail.workers.dev` and `INFRA_COORDINATION_ENABLED=true` on **each** controller. Ensure both controllers refer to the same D1 Worker and keys. Deploy the controller files on both Render instances, then verify `/infra/status`, `/infra/sla/status`, router preferences, and the watchdog's actual recent execution. Other internet-accessible endpoints must retain their existing auth.

## Switch and recovery

Use `POST /infra/failover` with `target_postgres`, `target_render`, `target_b2` explicitly chosen, `switch_router=true` and `quiesce_source=true`. A Render-only switch keeps the existing Postgres and B2 slots. For database switches, select the existing healthy paired Render slot or another prepared pair. First use the API's `dry_run` option and review the current and target fields; then run an attended failover and verify n8n workflows, credentials, SH01 jobs, media URLs and database writes. Each additional Render pair must be in the registry and pass the paired readiness checks.

The one-way database boundary is `ALTER SUBSCRIPTION ... DISABLE` after the write marker arrives. If any later step fails, the routers remain closed. Investigate the actual active database, subscription state, both Render service suspension states, D1 active slot, router targets, and logs before reopening. **Never automatically switch back to the old publisher after new writes.** To make the old database a standby, rebuild it from the new source through a separately reviewed empty destination bootstrap.

If the publisher is unreachable, the barrier cannot be produced: the system deliberately refuses automatic promotion. Investigate database outage, backups and possible data loss before a manually approved recovery. Monitor the replication slot WAL retention and backup status; stalled subscriptions can consume disk. Do not rely on Supabase free-tier inactivity emails as a transactional failover signal. Paid projects avoid free-tier inactivity pausing; verify your project plans and current policies in Supabase.

## What remains operationally required

- Verify real project permissions, direct connectivity, subscription creation, table copy and WAL retention. The local tests mock databases and Render; they are no substitute for a full staging drill.
- `public` is the replicated scope. Other schemas, out-of-band database writers, Supabase Auth/Storage, provider metadata and arbitrary functions/extensions are outside this mechanism. Keep them out of n8n's production dependency or design separate replication.
- D1 serializes controller decisions, while the Cloudflare n8n/SH01 routers use separate KV state and their mutation APIs do not accept fencing generations. A controller that loses the lease between checking and sending a remote command could still finish a command. Strong, end-to-end single-writer guarantees require router-level fencing and end-to-end drills.
- B2 currently has one bucket and no recovery member. Any B2 outage remains a system outage; adding another registered bucket alone does not make existing objects available there.
